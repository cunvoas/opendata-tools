OpenData

L'application s'appuie volontairement sur des données ouvertes et des référentiels publics. L'OpenData n'est pas ici un simple catalogue : c'est la chaîne de référence qui relie un territoire, ses communes, ses parcs, sa population et ses limites administratives.

Un même objet peut venir de plusieurs sources. La règle est de conserver la source d'origine, de rattacher l'objet à un code INSEE, puis de qualifier les données avant de les utiliser dans les calculs.
Les données généralistes
Niveau Rôle métier Point de vigilance
Région Regroupement administratif supérieur. Sert à organiser la navigation, les tableaux de bord et les exports. Une région ne porte pas directement les parcs : elle agrège des EPCI et des communes.
EPCI Établissement public de coopération intercommunale : communauté de communes, d'agglomération, métropole. C'est souvent l'unité de publication cartographique. Les limites et les compétences varient dans le temps. Un EPCI peut changer de nom, de périmètre ou fusionner.
Commune Point d'entrée principal : code INSEE, nom, rattachement à l'EPCI et à la région. Presque toutes les données métier sont rattachées à une commune. Le code INSEE est la clé stable. Le nom seul n'est pas une clé fiable.
Cadastre Contour administratif de la commune, utilisé pour rattacher les parcs et vérifier les limites du territoire. Dans cette application, le cadastre fournit le contour communal, pas le parcellaire individuel.
Densité INSEE Classe la commune en zone dense ou périurbaine. Les communes des catégories 1 et 2 de l'INSEE sont considérées comme denses. Si la commune est absente du référentiel, elle est traitée par défaut comme dense. C'est un choix à vérifier lors d'un ajout de territoire.
Adresse Géocodage des adresses lors de la saisie et de la localisation des parcs. Le géocodage donne un point ; il ne remplace pas le contour du parc.
Chaîne de rattachement
  1. Import : les données publiques sont chargées dans les référentiels territoriaux (régions, EPCI, communes, cadastre).
  2. Rattachement : un parc, une entrée ou un carreau est rattaché à une commune par son code INSEE. Les objets à cheval sur plusieurs communes peuvent porter un code composite.
  3. Contrôle spatial : les intersections et les contenances sont vérifiées entre commune, parc, carreau et isochrone.
  4. Qualification : les données ambiguës restent « à qualifier » et ne sont pas utilisées comme vérité terrain tant qu'elles ne sont pas validées.
  5. Publication : les données calculées sont exportées pour la carte publique, par EPCI.
Limites à connaître
  • Les portails open data n'ont ni les mêmes dates, ni les mêmes nomenclatures, ni la même qualité de géométrie.
  • Un contour communal peut être simplifié pour la carte : il ne faut pas l'utiliser pour un calcul cadastral fin.
  • Les données doivent être réimportées lorsque la collectivité publie une nouvelle version ; l'application ne devine pas les mises à jour.
  • Les licences diffèrent : Etalab pour une grande partie des données publiques françaises, ODbL pour OpenStreetMap. Toute réutilisation doit conserver l'attribution.

Parcs et OpenStreetMap

Le référentiel des parcs combine des jeux open data publiés par les collectivités, OpenStreetMap via le service Overpass, et un travail de qualification / complétion par les contributeurs. Aucune source n'est considérée comme parfaite : elles se complètent.

Open data des collectivités

Des imports dédiés existent pour plusieurs territoires :

  • Métropole Européenne de Lille (MEL), dont Lille, Roubaix, Tourcoing et Villeneuve-d'Ascq ;
  • Lyon ;
  • Toulouse ;
  • Nantes ;
  • jardins familiaux de Roubaix.

Les jeux locaux apportent souvent le nom, la surface, le type ou l'ouverture. Ils sont normalisés puis rattachés à la commune.

OpenStreetMap / Overpass

Le service Overpass interroge OpenStreetMap par emprise ou par commune. Il permet de récupérer les objets de type parc, jardin, square et leurs contours.

Les objets sont conservés avec leur identifiant OpenStreetMap, leur nom, leur contour, leur surface, leurs horaires et le code INSEE de rattachement.

Overpass est un service public gratuit : les échanges doivent rester ciblés et raisonnables.

De la donnée brute au parc métier
  1. Import local : le parc est enregistré avec sa source (donnée de la métropole, opendata, préfecture, OpenStreetMap) et un statut de qualification.
  2. Rattachement OSM : le contour cadastral de chaque commune est comparé avec le parc Overpass pour trouver la commune d'appartenance. Si un parc chevauche plusieurs communes, un code INSEE composite est conservé.
  3. Appariement : la recherche vérifie si un parc existant est contenu dans la géométrie OSM, ou si son contour intersecte celui d'OpenStreetMap.
  4. Enrichissement : si le parc existant n'a pas de contour, de surface ou d'horaires, les valeurs OpenStreetMap sont recopiées. Les noms et quartiers déjà saisis sont conservés.
  5. Création si absent : un parc OpenStreetMap sans équivalent est créé « à qualifier ». Il devra être vérifié avant d'être considéré comme un espace vert de référence.
  6. Entrées et isochrones : les entrées sont saisies ou complétées par les contributeurs. Chaque entrée reçoit ensuite une isochrone IGN, qui porte l'accessibilité piétonne du parc.
Corriger le détourage, saisir les entrées, fusionner les isochrones

Le détourage OpenStreetMap est un point de départ, pas une vérité cadastrale. Le contributeur peut corriger le contour, ajouter les accès réels du parc, puis fusionner les zones accessibles de chaque entrée pour obtenir l'emprise utilisée dans les calculs.

1Corriger le détourage
  1. Ouvrir la fiche du parc dans l'éditeur de parc.
  2. Afficher le cadastre et la couche des parcs OpenStreetMap pour situer le terrain.
  3. Lorsqu'un contour OpenStreetMap est proposé pour un parc qui n'en a pas encore, cliquer sur le tracé bleu et accepter « recopier le détourage ».
  4. Utiliser l'outil polygone pour dessiner le contour, puis les outils de modification pour déplacer, ajouter ou supprimer des sommets. Pour repartir de zéro, supprimer l'ancien tracé puis en dessiner un nouveau.
  5. Enregistrer : la surface du contour est recalculée. Le tracé doit rester un polygone simple, sans auto-intersection.
2Saisir les entrées
  1. Depuis la fiche du parc, ouvrir « Editer les entrées ».
  2. Utiliser le bouton de mode pour passer en « Mode ajout ».
  3. Cliquer sur la carte au niveau de l'accès réel, puis faire glisser le repère pour ajuster la position.
  4. Renseigner un nom explicite (« Entrée ouest », « Accès rue… »), un lien utile et, si besoin, la date.
  5. Cliquer « Valider » : l'entrée est enregistrée. Si le point est nouveau ou déplacé, son isochrone IGN est calculée pour 5 minutes de marche en zone dense, 20 minutes sinon.
  6. Répéter pour chaque accès, puis cocher « Afficher les isochrones » pour contrôler le résultat.
3Fusionner les isochrones
  1. Vérifier que toutes les entrées sont validées et disposent d'une isochrone.
  2. Cliquer sur « Fusionner les entrées ».
  3. Le contour du parc, lorsqu'il est présent, sert de base ; chaque isochrone d'entrée est ensuite ajoutée par fusion, sans trou.
  4. Le résultat devient l'emprise accessible du parc, utilisée pour croiser les carreaux et la population.
  5. Après tout ajout ou modification d'entrée, valider puis relancer la fusion.
Ordre important : « Fusionner les entrées » ne sauvegarde pas l'entrée en cours. Il faut d'abord cliquer « Valider ». Si une entrée n'a pas d'isochrone ou si le contour est invalide, la fusion peut échouer : corriger la géométrie puis recommencer.
Ce qui compte comme espace vert

L'application distingue les parcs et jardins publics de proximité des autres espaces. Certaines collectivités comptabilisent des cimetières, des bosquets ou des places minéralisées. Ces objets peuvent rester visibles dans les détails, mais ils ne sont pas retenus dans la surface OMS.

Le type de parc détermine s'il compte dans le calcul OMS. Un parc peut aussi être marqué manuellement comme OMS ou non OMS lorsqu'il existe un cas particulier.

Limites
  • Un objet OSM peut être incomplet, déplacé ou fusionné avec un autre.
  • Les surfaces OSM et locales peuvent différer.
  • Un parc sans entrée saisie n'a pas d'isochrone exploitable.
  • La présence d'un parc dans OSM ne prouve pas son accès public réel.
  • La qualification humaine reste indispensable avant publication.

INSEE et IGN

INSEE fournit la population et la maille de calcul ; IGN fournit le réseau piéton et les isochrones. Le croisement des deux permet de passer d'une surface de parc à une population réellement couverte.

INSEE : Filosofi et carreaux de 200 m

La population utilisée est issue des données carroyées Filosofi 200 m de l'INSEE. Chaque carreau est une maille carrée de 200 m × 200 m, soit 40 000 m², identifiée par un code de carreau.

Les données Filosofi 200 m conservent notamment :

  • la population totale et les classes d'âge ;
  • le nombre de ménages et leur composition ;
  • les indicateurs de revenu et de pauvreté ;
  • les logements par époque de construction et le logement social.
  • l'année de référence : 2015, 2017, 2019, 2021 ;
  • le carreau de 1 km parent ;
  • le code officiel géographique ;
  • l'indicateur d'imputation de la valeur.

Le calcul V4 charge la population Filosofi en une seule fois sur l'union du carreau courant et des parcs qui l'intersectent. Il évite ainsi un chargement par carreau.

IGN : l'isochrone piétonne

Une isochrone est la zone atteignable à pied depuis un point de départ en un temps donné. Elle ne représente pas un cercle : elle suit le réseau de rues, les passages piétons et les obstacles. L'application appelle le service d'isochrones de l'IGN (Géoplateforme), avec le profil piéton et le réseau de rues de la base IGN.

Contexte Temps OMS Distance indicative Surface minimale Surface conseillée
Zone dense (INSEE 1 ou 2) 5 min, soit 300 s environ 300 m 10 m²/habitant 12 m²/habitant
Zone périurbaine 20 min, soit 1 200 s environ 1 200 m 25 m²/habitant 45 m²/habitant

Le paramètre transmis à l'IGN est un temps en secondes. Les valeurs 300 et 1 200 sont donc des temps, pas des distances à vol d'oiseau. La distance réelle parcourue peut être supérieure à 300 m ou 1 200 m.

Fichiers de localisation

Le calcul ne travaille jamais sur un point isolé : il s'appuie sur les contours et les positions du territoire. Les principales localisations sont :

Population couverte et prorata

La zone d'accessibilité d'un parc est comparée aux carreaux INSEE de 200 m. Pour chaque carreau touché :

  • si le carreau est entièrement couvert par la zone accessible, toute sa population est comptée ;
  • si le carreau est partiellement couvert, la population est estimée au prorata de la surface d'intersection.
population_contribuée = population_carreau × (surface_intersection / 40 000 m²)
Limites
  • L'isochrone dépend de la qualité du réseau IGN et de la date de la base.
  • Les barrières physiques, les horaires ou les fermetures ne sont pas tous modélisés.
  • La population est annuelle et carroyée : elle ne représente pas une fréquentation réelle.
  • Le prorata suppose une population uniformément répartie dans le carreau, ce qui est une approximation.
  • Une commune absente du référentiel de densité est traitée par défaut comme dense : le résultat doit être vérifié.

NDVI

Le NDVI (Normalized Difference Vegetation Index) mesure la vigueur de la végétation à partir d'images satellite. Il ne remplace pas la surface OMS : il apporte une lecture de la végétation réelle à l'intérieur du parc.

Ce que mesure le NDVI
NDVI = (proche infrarouge − rouge) / (proche infrarouge + rouge)
     = (B08 − B04) / (B08 + B04)

Le résultat est compris entre -1 et 1 :

  • valeurs élevées : végétation dense, active ;
  • valeurs moyennes : pelouse, végétation clairsemée ;
  • valeurs faibles ou négatives : sol nu, minéral, eau, ombre ou nuage.

L'application conserve la moyenne, le minimum, le maximum, l'écart-type et la date d'acquisition. Un parc très minéralisé peut donc avoir une surface OMS correcte mais un NDVI faible.

Source
  • Sentinel-2 L2A (réflectance de surface) ;
  • Copernicus Data Space Ecosystem (CDSE) ;
  • mosaïque : l'image la moins nuageuse ;
  • masque de qualité : nuages, ombres, eau et pixels saturés exclus ;
  • calcul statistique côté fournisseur : aucune image n'est téléchargée.
Traitement dans l'application
  1. Déclenchement : le NDVI est demandé pendant le calcul d'un parc, via le bouton « Calculer le parc », ou par la file de traitement.
  2. Fenêtre : l'appel porte sur l'année précédente, sur une fenêtre estivale configurable (par défaut du 1er au 15 juin, avec une fenêtre de secours fin juin).
  3. Un seul appel par parc et par année de référence : le NDVI Copernicus est lissé sur plusieurs années. Une seule réponse est recopiée sur tous les résultats annuels du parc pour économiser le quota.
  4. File persistante : les demandes sont traitées par lots de 10 toutes les 5 minutes. Les traitements bloqués en cours sont recyclés, et les erreurs sont rejouées quotidiennement.
  5. Historique : chaque réponse contenant des statistiques est conservée avec la période, le nombre de pixels valides et les valeurs. Cet historique n'est pas dédoublonné : il garde la trace de chaque observation.
  6. Non bloquant : une erreur réseau, un quota dépassé ou un timeout laisse les colonnes NDVI vides et n'empêche pas le calcul OMS de se terminer.
Usages
  • repérer les parcs minéralisés ou peu végétalisés ;
  • comparer la végétation entre quartiers ou entre années ;
  • suivre l'effet de travaux de végétalisation ;
  • compléter l'analyse OMS par une lecture écologique du parc.
Limites
  • Le NDVI n'est pas un critère de surface OMS : il ne remplace ni les m²/habitant ni l'accessibilité.
  • Une même valeur est recopiée sur toutes les années du parc tant que la reventilation par période n'est pas faite.
  • Le satellite ne repasse pas tous les ans au même endroit ; certaines fenêtres restent sans donnée exploitable.
  • Le masque de nuages peut retirer une partie du parc et fausser la moyenne.
  • La fonctionnalité est désactivée par défaut tant que les identifiants CDSE ne sont pas configurés.

Les calculs

Le moteur de calcul V4 transforme une grille de carreaux INSEE, des parcs et des isochrones en indicateurs de surface accessible par habitant, comparés aux seuils OMS.

Un carreau fait 200 m × 200 m, soit 40 000 m². Le calcul est mené pour chaque carreau et chaque année de population INSEE. Le résultat est conservé pour chaque carreau et chaque année.
Déroulé du calcul
  1. Carreau et densité : identification du carreau, de sa géométrie et de la commune. La densité INSEE détermine le seuil et le temps d'accès.
  2. Parcs intersectants : recherche spatiale de tous les parcs dont le polygone touche le carreau.
  3. Population groupée : chargement des carreaux Filosofi couvrant le carreau et les zones d'influence des parcs.
  4. Calcul par parc : pour chaque parc actif à l'année traitée, récupération ou calcul de son résultat : surface du parc, population couverte, surface par habitant.
  5. Unions : union des polygones de tous les parcs, des parcs OMS, et des parcs OMS « durables » (surface supérieure au seuil minimal, 5 000 m² par défaut).
  6. Population dans l'isochrone : intersection de l'union avec les carreaux INSEE et proratisation de la population selon la surface couverte.
  7. Indicateurs : surface par habitant, population incluse / exclue, surface manquante pour le minimum et pour la recommandation, indicateur de parc durable.
Formules
population_contribuée =
  population_carreau × (surface_intersection / 40 000)

surface_par_habitant =
  surface_totale_des_parcs_accessibles / population_dans_l_isochrone

surface_manquante =
  MAX(0, seuil_OMS × population_dans_l_isochrone
           − surface_totale_des_parcs_OMS)

Le calcul est appliqué deux fois : sur le périmètre « tous parcs » et sur le périmètre « parcs OMS ». Les parcs non OMS restent visibles dans les détails, mais ne comptent pas dans la surface OMS.

Optimisations V4
  • Chargement groupé : la population Filosofi est lue en une seule fois au lieu d'une lecture par carreau.
  • Cache de surface : les intersections déjà calculées sont réutilisées.
  • Mutualisation : quand tous les parcs d'un carreau sont OMS, les résultats « tous parcs » et « OMS » sont calculés une seule fois.
  • Constante de surface : 40 000 m² est partagé par tous les calculs de prorata.
  • Bascule : le moteur V4 peut être remplacé par une version antérieure si nécessaire.
Limites
  • La population est celle de l'année INSEE disponible ; le résultat n'est pas temps réel.
  • Le prorata suppose une répartition uniforme de la population dans chaque carreau.
  • La qualité de l'isochrone dépend du réseau IGN et de la saisie des entrées.
  • Un parc sans entrée ou sans géométrie ne peut pas être correctement pris en compte.
  • Les changements de contour de parc ou de commune nécessitent un recalcul.

Les propositions

Les propositions répondent à une question simple : où créer ou agrandir un parc pour réduire le déficit d'espaces verts par habitant ? Plusieurs algorithmes coexistent, avec des compromis différents entre rapidité, qualité de la distribution et surface totale proposée. Une méthode manuelle permet aussi de dessiner une proposition et d'en suivre l'impact au fil de l'eau.

Données d'entrée communes
  • les carreaux INSEE 200 m de la commune ;
  • la population et la surface accessible par carreau ;
  • le déficit par rapport au seuil minimal et à la recommandation OMS ;
  • le rayon de propagation : 300 m en zone dense, 1 200 m en zone périurbaine ;
  • les seuils de surface : minimum acceptable de 650 m² pour une proposition, parc « durable » à partir de 5 000 m².
Méthode manuelle : dessiner et évaluer au fil de l'eau

L'utilisateur peut choisir lui-même l'emplacement d'un parc, sans passer par un algorithme. Il dessine une proposition sur la carte, l'enregistre, puis mesure immédiatement son effet sur les indicateurs OMS de la commune.

Cercle

Un point et un diamètre suffisent. C'est le mode rapide pour tester une idée ou estimer l'ordre de grandeur d'un parc.

Polygone

Le contour est tracé librement pour coller à la forme réelle du terrain. C'est le mode précis pour une proposition argumentée.

Principe de l'évaluation au fil de l'eau

  1. Choisir la commune et l'année INSEE de travail.
  2. Dessiner une proposition, lui donner un nom, une surface ou un diamètre, puis l'enregistrer.
  3. Lancer l'évaluation : toutes les propositions manuelles de la commune et de l'année sont prises en compte.
  4. La carte affiche, pour chaque carreau, la surface manquante avant et après, la surface accessible ajoutée et la nouvelle surface par habitant.
  5. Ajouter, modifier ou supprimer une proposition, puis relancer l'évaluation : le résultat est remplacé à chaque nouveau calcul.
L'évaluation manuelle utilise une distance à vol d'oiseau, avec une marge de tolérance autour du seuil OMS. Elle ne remplace pas l'isochrone piétonne utilisée pour les parcs existants : elle donne une tendance rapide, à confirmer par une analyse plus fine. Seuls les carreaux déjà calculés pour l'année sont évalués.
Algorithmes actifs
Méthode Principe Point fort Limite
Glouton par déficit Traiter le carreau au plus fort déficit, puis propager aux voisins. Simple, rapide, facile à expliquer. Solution locale, dépend de l'ordre de traitement.
Glouton par population Variante qui priorise le déficit multiplié par la population. Favorise l'impact humain total. Même logique gloutonne.
Regroupement DBSCAN Regroupe les carreaux déficitaires en zones avant d'itérer. Meilleure lecture spatiale des grappes de déficit. Paramétrage du regroupement à surveiller.
Programmation par contraintes Optimisation sur des sous-ensembles de carreaux non voisins, avec des contraintes de surface et de déficit. Optimisation locale explicite, meilleure distribution. Plus coûteux ; passe finale nécessaire pour les zones bloquées.
Moindres carrés (χ²) Le χ² sert de filtre de convergence ; le montant proposé reste le déficit complet. Bonne stabilité, montants non sous-estimés. Boucle plus longue ; le χ² n'optimise pas directement la surface.
Algorithme génétique Chaque solution associe une surface de parc à chaque carreau. Exploration globale, bonne réduction du déficit. Temps de calcul plus long ; résultat non déterministe.
Programmation par contraintes

Programmation par contraintes sur des sous-ensembles de carreaux non voisins.

  • discrétisation en unités de 500 m² ;
  • maximum 80 unités par carreau (40 000 m²) ;
  • sélection d'environ 20 % des carreaux non voisins à chaque itération ;
  • objectif : minimiser d'abord les écarts résiduels, ensuite la surface ajoutée ;
  • repli sur une méthode gloutonne si le solveur échoue.
Moindres carrés (χ²)

Moindres carrés pondérés par la population.

  • le χ² estime une moyenne pondérée du déficit ;
  • il sert de filtre d'arrêt et de journal, pas de plafond de surface ;
  • le carreau choisi est celui du plus fort déficit ;
  • la surface proposée est le déficit complet, plafonnée à 40 000 m² ;
  • la surface accessible est propagée aux voisins dans le rayon OMS.

L'ancienne version plafonnait au χ² et sous-estimait les surfaces d'environ 38 %.

Algorithme génétique

Algorithme génétique : chaque solution candidate associe une surface de parc à chaque carreau.

  • une surface proposée par carreau, entre 0 et 40 000 m² ;
  • population de 200 à 2 000 solutions, 300 générations ;
  • croisement uniforme (0,9), mutation gaussienne (0,25), élitisme 5 % ;
  • score : réduction du déficit × population, moins une pénalité de parcimonie de 5 % ;
  • balayage final pour les zones restées déficitaires.

Le résultat est une aide à la décision, pas une localisation cadastrale exacte.

Limites et bonnes pratiques
  • Une proposition indique une surface à créer dans un carreau, pas un terrain disponible ni un projet validé.
  • Les algorithmes ne connaissent ni le prix du foncier, ni le PLU, ni la pollution, ni la volonté politique.
  • Deux algorithmes peuvent proposer des distributions différentes pour un même déficit.
  • Les surfaces inférieures à 650 m² ne sont pas retenues ; un parc est considéré « durable » à partir de 5 000 m².
  • Toute proposition doit être confrontée au terrain, aux services techniques et à la population avant décision.
